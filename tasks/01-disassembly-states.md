# T-01: Состояния разборки в build-scene

- **Статус:** готово
- **Приоритет:** high
- **Оценка:** L (3+ недели; включает исследовательскую фазу)
- **Зависимости:** нет
- **Квартал roadmap:** Q1 2027

## Цель

`build-scene` умеет строить только собранное оружие. Игра целиком про
разборку и сборку — добавить в экспорт сцен состояния разборки, чтобы
одной командой можно было получить AK-47 в состоянии неполной разборки
(field strip), «взрыв-схемы» (exploded view) и полного разбора на части.

```bash
wog-dump build-scene ak47                          # как сейчас — собранное
wog-dump build-scene ak47 --state field-strip      # неполная разборка
wog-dump build-scene ak47 --state exploded         # взрыв-схема
wog-dump build-scene ak47 --state parts            # полный разбор, части разложены
```

## Контекст: что уже есть в коде

- `core/scene.py::SceneBuilder.build_scene()` (строки ~162) строит дерево
  `_GameObjectInfo` из decrypted-бандла и пишет GLB через `core/glb.py`.
- `_read_part_lists()` (`core/scene.py:632`) уже читает TextAsset-ы
  `{weapon}_parts` и `{weapon}_field_strip` и кладёт списки имён в
  `SceneStats.parts` / `SceneStats.field_strip`. Сейчас списки используются
  только для манифеста `scene.json`.
- `classify_game_object()` (`core/scene.py:121`) размечает UI-стрелки,
  cutaway-меши и VFX — они скрываются/показываются через `--extras`.
- Скрытие объектов уже реализовано для extras: узел либо не эмитится,
  либо эмитится скрытым — переиспользовать этот механизм для field-strip.

## Фаза R (research spike, 3–5 дней, обязательна)

До написания продакшн-кода исследовать на реальных decrypted-бандлах
(ak47, glock17, m4a1 — уже есть в `runtime/decrypted/`):

1. **Формат `{weapon}_parts` / `{weapon}_field_strip` TextAsset** — полный
   дамп нескольких файлов, не только первые колонки. Есть ли порядок
   разборки, есть ли координаты/направления снятия деталей?
2. **AnimationClip-ы в бандле** — содержат ли кривые перемещения деталей
   при разборке (`m_PositionCurves` / bindings на Transform). Если да —
   это готовые векторы движения для exploded view.
3. **Служебные TextAsset-ы** с похожими именами (`*_assembly`, `*_steps`) —
   что в них.

Результат фазы — короткая заметка `docs/research-disassembly-data.md`:
какие данные доступны, что решено использовать для каждого состояния.
Дальнейшие пункты обновить по её итогам.

## Требования

### Функциональные

- `--state {assembled,field-strip,exploded,parts}`, дефолт `assembled`
  (обратная совместимость: поведение без флага не меняется).
- `field-strip`: части из списка `field_strip` отделяются от оружия
  и кладутся рядом с ним в плоскости стола (поза «разложено на коврике»).
- `exploded`: все части остаются, но смещаются вдоль направления снятия
  (из фазы R) или, если направление неизвестно, радиально от центроида
  оружия вдоль локальной оси детали. Расстояние — `--explode-distance`
  в метрах, дефолт пропорционален габаритам оружия.
- `parts`: плоская раскладка всех мешей сеткой (grid packing) — удобно
  для просмотра/печати по частям.
- Именование вывода: `runtime/scenes/<weapon>/` для assembled,
  `runtime/scenes/<weapon>-<state>/` для остальных состояний.
- `scene.json` каждого состояния содержит `"state"` и фактически
  применённые смещения частей.

### Нефункциональные

- Никаких изменений в GLB-writer, кроме уже существующих возможностей
  (смещения делаются на уровне `_GameObjectInfo` до эмиссии узлов).
- mypy strict, тесты — по конвенциям проекта (`tests/unit/test_scene.py`).

## План реализации

1. Фаза R (выше).
2. `SceneStats` + новая dataclass `PartPlacement` (имя, узел, смещение).
3. Модуль `core/scene_states.py`: чистые функции
   `apply_field_strip(tree, lists, ...) -> tree`, `apply_exploded(...)`,
   `apply_grid_layout(...)` — принимают и возвращают `_GameObjectInfo`,
   без I/O. Вызываются из `build_scene()` до `_emit_nodes()`.
4. CLI-флаг в `cli/scene.py`, проброс в `SceneBuilder`.
5. Манифест: секция `state`.

## Критерии приёмки

- [ ] Заметка фазы R лежит в `docs/`
- [ ] Все 4 состояния строятся для ak47 из локального кэша без сети
- [ ] `--state assembled` байт-в-байт даёт тот же GLB, что текущая версия
      (проверить на фиксируемом входе)
- [ ] field-strip выглядит как неполная разборка: детали сняты, а не
      отсутствуют (детали видны в сцене рядом)
- [ ] `scene.json` валиден, содержит state и смещения
- [ ] Юнит-тесты покрывают все 3 новых состояния на синтетическом дереве

## Тесты

- Синтетическое дерево `_GameObjectInfo` + фикстуры списков частей —
  проверка смещений и скрытий per-state.
- Snapshot-тест GLB: assemble-путь не регрессирует.
- Integration (`pytest -m live` или на локальном кэше): ak47 во всех
  состояниях открывается в Blender без ошибок импорта.

## Риски и открытые вопросы

- Направления снятия деталей могут не храниться в бандле явно — тогда
  exploded view строится эвристикой (радиально + вдоль локальной оси).
  Это приемлемо, но зафиксировать в заметке фазы R.
- Имена в списках частей могут не совпадать 1:1 с именами GameObject-ов —
  потребуется нормализация имён (префиксы/суффиксы); собрать правила
  на фазе R по нескольким оружием.
