# T-08: Локализация CLI

- **Статус:** готово
- **Приоритет:** low
- **Оценка:** M
- **Зависимости:** нет
- **Квартал roadmap:** Q2 2027

## Цель

Пользовательский вывод CLI на русском для русскоязычной аудитории
проекта (и фундамент для других языков). Технические логи остаются
на английском — локализуются только сообщения, которые видит
пользователь в нормальном режиме работы.

```bash
wog-dump --locale ru full-pipeline
# или постоянно: WOG_LOCALE=ru / .env
```

## Контекст: что уже есть в коде

- Все пользовательские строки — `click.echo(...)` в модулях
  `cli/*.py`; ошибки пользователя — `cli/errors.py::error_handler`
  превращает доменные исключения в однострочные сообщения.
- `core/config.py` — Pydantic-settings: `api_lang` (WOG_LANG) уже
  существует, но это язык запросов к API игры — **не путать**;
  новый параметр назвать `locale` / `WOG_LOCALE`.
- Rich используется для вывода — локализованный текст проходит тем
  же путём, никаких отдельных механизмов не нужно.

## Требования

### Функциональные

- `--locale {en,ru}` глобальный флаг CLI + настройка `WOG_LOCALE`
  в конфиге/.env (дефолт `en`; флаг CLI сильнее env).
- Локализуются: все `click.echo`-сообщения команд (info, catalog,
  login/logout/register, download-*, decrypt, unpack, build-scene,
  full-pipeline, cache), тексты об ошибках из `cli/errors.py`,
  вопросы-подтверждения (`click.confirm`).
- НЕ локализуются: логи логгера (stderr, технические), tracebacks,
  справка `--help` (объём большой; вынести в отдельный этап, см.
  «Открытые вопросы»).
- Формы множественного числа: «скачано 3 файла / 5 файлов / 21 файл» —
  через plural-правила в каталоге (для ru — три формы), не через
  `f"{n} file(s)"`.
- `wog-dump info` показывает текущую locale.

### Нефункциональные

- Механизм: `gettext` из stdlib с каталогами `resources/locales/
  <lang>/LC_MESSAGES/wog_dump.po/.mo`; сборка .mo — скриптом
  `scripts/compile_locales.py` (запускать при сборке пакета — шаг
  в pyproject/wheel или ленивая загрузка .po при отсутствии .mo,
  чтобы git clone работал без шага компиляции).
- Обёртка `utils/i18n.py`: `t(msgid, **format)`, `tn(msgid, n)` —
  единая точка, никакого прямого `gettext.gettext` в cli-модулях.
- Английские строки остаются исходниками в коде (msgid = английский
  текст) — переключение на несуществующий locale = английский,
  никаких ошибок.

## План реализации

1. `utils/i18n.py`: инициализация gettext (fallback English),
   `t()`/`tn()`, установка locale из конфига.
2. Инвентаризация строк: `grep click.echo src/wog_dump/cli` — список
   (ожидаются сотни строк; выполнить по модулям, начиная с
   высокочастотных: `download`, `pipeline`, `info`, `errors`).
3. Русский каталог `.po`; правила plural для ru.
4. `--locale` в `cli/main.py` + `locale` в `core/config.py`.
5. `scripts/compile_locales.py` + подключение к сборке wheel.

## Критерии приёмки

- [ ] `wog-dump --locale ru info` и `full-pipeline` (сухой прогон на
      существующем кэше) выводят русский текст без английских
      вставок, кроме технических терминов (bundle, GLB)
- [ ] Числовые сообщения согласованы по падежам (3 файла, 5 файлов)
- [ ] `--locale en` и дефолт байт-в-байт сохраняют текущий вывод
- [ ] Несуществующая locale → тихий fallback на английский
- [ ] Юнит-тест t()/tn() на фикстурах каталога (en/ru)

## Тесты

- `tests/unit/test_i18n.py`: загрузка каталогов, fallback, plural.
- CLI-тест: ключевые команды в `--locale ru` не содержат msgid-строк
  в выводе (выборочная проверка высокочастотных сообщений).

## Риски и открытые вопросы

- Объём перевода — сотни строк; ограничить scope задачи переводом
  пользовательских сообщений (не --help, не доки). Помощь `--help`
  локализовать отдельным продолжением, если понадобится.
- Двуязычные релизные заметки — вне этой задачи (решение принять
  отдельно: ru-секция в CHANGELOG или нет).
