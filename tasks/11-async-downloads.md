# T-11: Асинхронные загрузки (httpx/asyncio)

- **Статус:** не начата
- **Приоритет:** medium
- **Оценка:** L (2–3 недели, включая сравнительное тестирование)
- **Зависимости:** нет
- **Квартал roadmap:** Q3 2027

## Цель

Замена потоковой модели загрузок (ThreadPoolExecutor + requests) на
asyncio + httpx.AsyncClient. Полный каталог — 10–20 ГБ и сотни файлов;
цель — измеримое ускорение (меньше накладных расходов на потоки,
лучший пулинг соединений) при сохранении всех гарантий текущей
реализации: rate-limit, resume, валидация размеров.

## Контекст: что уже есть в коде

- `core/download.py::DownloadManager` (651 строка):
  - `_fetch_asset()` — скачивание одного актива c `Range`-resume;
  - `_prepare_resume()` — resume через `.tmp.meta` сайдкар
    (валидатор из security-харднинга v2.6);
  - `validate_asset()` — сверка с server-declared size;
  - `download_assets()` / `download_assets_batched()` — параллелизм
    на потоках, `max_threads` из конфига;
  - `check_for_updates()` / `check_asset_needs_update()`.
- `core/http.py` — общая сессия (retries, pooling) и `RateLimiter`
  (синхронный, на потоки).
- `core/api.py` / `core/auth.py` — отдельный путь (query-API, мелкие
  последовательные запросы) — их эта задача НЕ трогает.

## Требования

### Функциональные (паритет поведения — главное требование)

- Полный паритет текущего API: сигнатуры и семантика публичных
  методов `DownloadManager` не меняются (`download_assets(...)`
  остаются синхронными — внутри `asyncio.run(...)`; CLI и
  `full-pipeline` не переписываются).
- Rate-limit: эквивалент на asyncio (`asyncio.Semaphore(max_threads)`
  + асинхронный rate-limiter с теми же параметрами из конфига);
  параметры конфига (`max_threads`, rate) действуют как раньше.
- Resume: `.tmp.meta` сайдкар и `Range`-логика — без изменений
  формата; недокачанный старой версией файл докачивается новой.
- Валидация размеров и реакция на 404/ошибки — идентичны текущим
  (тесты на моках фиксируют поведение заранее).
- httpx только для загрузок ассетов; api.py/auth остаются на
  requests (не смешивать слои в одной задаче).

### Нефункциональные

- Замер до/после: скрипт `scripts/bench_download.py` — прогон
  N=50 ассетов (реальный набор) на 4/8/16 потоках, секунды и
  пропускная способность; результаты зафиксировать в
  `docs/benchmarks-download.md` этой же задачей.
- Если ускорение < 15% на реалистичном профиле — задача
  останавливается и решение «откат/оставить» фиксируется в этом
  файле с данными (это допустимый исход, паритет и пулинг —
  тоже ценность).
- Мартовская гигиена: `requests` остаётся (api/auth), `httpx`
  добавляется в main deps.

## План реализации

1. Фиксация текущего поведения golden-тестами: мок-сервер
   (aiohttp.test_utils или responses-аналог для текущего кода) —
   кейсы: полный файл, докачка с середины, обрыв соединения,
   несовпадение размера, 404. Тесты пишутся против старого кода,
   должны пройти на новом без изменений.
2. `core/download_async.py`: асинхронная реализация одного актива
   (порт `_fetch_asset`/`_prepare_resume`), асинхронный rate-limiter.
3. Обвязка `download_assets_async` + синхронный фасад в
   `DownloadManager` (методы-обёртки, общий код валидации
   переиспользуется).
4. Бенчмарк, решение по результатам.
5. Переключение фасада на новую реализацию, старый потоковый путь
   удалить (не тащить оба).

## Критерии приёмки

- [ ] Все golden-тесты паритета проходят на новой реализации
- [ ] Resume: файл, докачанный после ручного обрыва старой версией,
      успешно докачивается новой (проверка на живом наборе)
- [ ] `docs/benchmarks-download.md` содержит таблицы до/после
- [ ] Публичный API DownloadManager не изменился (mypy + тесты
      интеграции CLI проходят без правок)
- [ ] `wog-dump full-pipeline` end-to-end на подмножестве оружий
      проходит без сети-моков (live, помеченный прогон)

## Тесты

  (фасад).

## Риски и открытые вопросы

- Скрытые зависимости от requests-сессии в валидации
  (`_response_validator`) — вынести в чистую функцию, использовать
  обеими реализациями.
- Windows ProactorEventLoop и лимиты файлов — контейнер/CI Linux,
  но задокументировать, если Windows-пользователи увидят отличия.
