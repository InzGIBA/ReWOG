# T-12: Content-addressed хранилище и cache --gc

- **Статус:** готово (отложено по порогу из раздела «Риски»: дубликаты 3.4% < 10%, см. «Итог»)
- **Приоритет:** low
- **Оценка:** M
- **Зависимости:** нет
- **Квартал roadmap:** Q3 2027

## Цель

Между оружиями много общих ресурсов (текстуры, меши, звуки), сейчас
каждый unpacked-файл лежит копией в своей папке оружия. Ввести
дедупликацию по хэшу содержимого с сохранением удобной per-weapon
структуры для пользователя и добавить `cache --gc` для очистки
мусора. Цель по диску — измеримое снижение объёма `unpacked/`
на полном каталоге.

## Контекст: что уже есть в коде

- `runtime/unpacked/<weapon>/...` — плоский вывод экстракторов
  (`core/unpack.py`), имённая адресация по папкам оружия.
- `cli/cache.py` — управление БД-кэшем; паттерн «разовая миграция
  с `--force`» уже существует (миграция legacy-txt импорта из v2.6).
- `core/database.py` — SQLite: таблицы weapons/keys/settings;
  файловые пути сюда не входят (расширение схемы — часть задачи).
- Важно: `runtime/encrypted/` и `runtime/decrypted/` НЕ трогаем —
  на них завязаны resume и валидация `core/download.py` /
  `core/decrypt.py`. Дедупликация только `unpacked/`.

## Требования

### Функциональные

- Новая схема хранения `unpacked/`: blobs в
  `runtime/unpacked/.store/ab/cd/<sha256>` + per-weapon манифест
  `unpacked/<weapon>/.manifest.json` (относительные пути → blob
  hash, тип, имя исходного объекта). Логическая адресация
  сохраняется: генерируются жёсткие ссылки (hardlinks) на блобы
  там же, где файл лежал бы в старой схеме — пользователь и
  инструменты видят прежние пути.
- `unpack-assets` пишет в новую схему (безусловная замена; старая
  раскладка читается всеми командами как раньше).
- `wog-dump cache --dedup-migrate`: разовая конверсия существующего
  `unpacked/` (паттерн как у существующей миграции: один раз на
  БД, `--force` для повтора; создаёт блобы+манифесты+ссылки,
  старые копии файлов заменяет ссылками).
- `wog-dump cache --gc`: удаляет блобы, на которые не ссылается ни
  один манифест; `--gc --dry-run` — только отчёт объёма; перед
  удалением — подтверждение (sum удаляемых байт).
- `wog-dump info` показывает: объём unpacked, сэкономлено дедупом
  (разница логического/физического объёма).

### Нефункциональные

- Хэш — sha256; считается потоково при записи (файл пишется один
  раз, хэш — по ходу записи, не отдельным проходом).
- Кросс-устройства: если hardlink невозможен (разные ФС, права) —
  fallback на копию + предупреждение; функциональность не зависит
  от типа ссылки.
- Манифесты — в БД не дублируются: манифест файловый, БД хранит
  только служебную запись о миграции (существующая таблица
  settings).
- Безопасность путей: новые типы имён (blob-пути) проходят через
  `core/paths.py::contained_path` — без новых «сырых» склеек путей.

## План реализации

1. `core/store.py`: `BlobStore` — put(bytes/path)→hash, open(hash),
   физический объём, сборка мусора по списку живых хэшей.
2. Интеграция в `AssetUnpacker`: запись экстрактов через BlobStore
   + манифест + hardlink на логический путь.
3. `cache --dedup-migrate` в `cli/cache.py`.
4. `cache --gc` (+ `--dry-run`), подтверждение, отчёт.
5. `info`: статистика экономии.

## Критерии приёмки

- [ ] После `unpack-assets` на 5+ оружиях с общими ресурсами:
      логических файлов ≥ физических блобов, все логические пути
      открываются и содержат корректные данные (байт-сравнение
      выборки со старой раскладкой до миграции)
- [ ] `--dedup-migrate` на существующем полном `unpacked/`
      проходит идемпотентно (повтор — no-op с сообщением)
- [ ] `--gc --dry-run` после удаления одного оружия из манифестов
      показывает ровно его уникальные блобы; `--gc` удаляет их
- [ ] `info` показывает экономию в человекочитаемом виде
- [ ] Юнит-тесты BlobStore и миграции на синтетических деревьях

## Тесты

- `tests/unit/test_store.py`: put/get, детект дубликатов, gc
  (живые/мёртвые блобы), hardlink-fallback (mock os.link OSError).
- `tests/unit/test_unpack.py`: расширить — запись через BlobStore,
  манифест корректен, логический путь существует.
- Интеграционный тест миграции: старое дерево → миграция →
  байт-идентичность выборки.

## Риски и открытые вопросы

- Реальная доля дубликатов неизвестна до замера: сначала мини-скрипт
  (sha256 по существующему unpacked, отчёт дубликатов) — если
  экономия < 10%, зафиксировать здесь и пересмотреть приоритет
  задачи (допустимо отложить в пользу 13-14).
- Windows NTFS hardlinks работают, но `--gc` на открытых файлах —
  обработать PermissionError как пропуск с отчётом.

## Итог (2026-11-10)

Замер из раздела «Риски» выполнен первым делом (scripts/audit_duplicates.py,
sha256 по всем 87 163 файлам runtime/unpacked, 11.91 ГБ):

- уникальных блобов 83 880, групп дубликатов 506, дублирующих файлов 3 789;
- съэкономить дедупликация может 0.4 ГБ, это 3.4% объёма;
- почти весь выигрыш — мелкие cutaway-текстуры (cuts.png повторяется
  в ~90 оружиях).

Порог 10% не достигнут, миграция на CAS и cache --gc отложены. Объём
работы (BlobStore, манифесты, миграция, gc) не окупается 0.4 ГБ.
Пересмотреть, если unpacked вырастет кратно или появятся сценарии,
где важен физический объём (ограниченные диски,Archive-публикации).
Аудиторский скрипт остаётся в scripts/ для повторного замера.
