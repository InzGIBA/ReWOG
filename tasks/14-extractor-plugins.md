# T-14: Плагины-экстракторы через entry points

- **Статус:** готово
- **Приоритет:** low
- **Оценка:** M
- **Зависимости:** нет
- **Квартал roadmap:** Q3 2027

## Цель

Открыть точку расширения: сторонний pip-пакет может добавить
обработчик нового типа Unity-объектов без форка ReWOG. Это путь
для сообщества (спрайты, шейдеры, новые типы после апдейтов Unity)
и дисциплина для самого проекта: встроенные экстракторы и плагины
работают через один механизм.

## Контекст: что уже есть в коде

- `core/unpack.py`: базовый класс `AssetExtractor` (методы
  `extract(obj, output_dir)`, `_extract_data(data, output_dir)`),
  встроенные экстракторы с `obj_type`, реестр
  `EXTRACTORS: dict[str, AssetExtractor]` (~строка 358),
  диспетчеризация в `AssetUnpacker` по `obj.type.name`.
- `unpack-assets --extract-types` уже фильтрует типы — UI-слова
  для плагинов уже существует.
- pyproject — hatchling; entry points через `[project.entry-points.<group>]`.

## Требования

### Функциональные

- Группа entry points: `wog_dump.extractors`. Плагин объявляет
  класс-наследник `AssetExtractor` (точка входа — сам класс или
  фабрика без аргументов).
- Загрузка при старте распаковки: встроенные + плагины;
  конфликт `obj_type` (плагин против встроенного) — плагин
  побеждает с предупреждением в лог (легальный способ
  переопределить поведение).
- Ошибка импорта одного плагина не рушит распаковку: warning в
  лог («плагин X не загрузился: <причина>»), остальные работают.
- `wog-dump unpack-assets --list-extractors`: таблица
  (тип, источник builtin/plugin, имя пакета).
- `extract(obj, output_dir)` плагина получает те же гарантии,
  что встроенные: путь обязан строиться через
  `core/paths.py::contained_path` (документировать в базовом
  классе; встроенная защита от path traversal остаётся на месте).

### Нефункциональные

- API расширения зафиксирован минимумом: `AssetExtractor` как есть,
  документация docstring-ами; никакой обязательной зависимости
  плагина от внутренностей `core/` кроме базового класса и
  `contained_path` (обе вещи — публичный API с этой задачи).
- Пример-плагин в репо: `examples/plugin-sprite/` — минимальный
  пакет (свой pyproject, entry point, README на полстраницы),
  устанавливаемый рядом для демонстрации.

## План реализации

1. `core/unpack.py`: функция `_load_plugin_extractors()` через
   `importlib.metadata.entry_points(group="wog_dump.extractors")`;
   слияние в реестр с приоритетом плагина; тёплый кэш на процесс.
2. `--list-extractors` в `cli/unpack.py`.
3. `examples/plugin-sprite/` (SpriteRenderer→PNG превью или
   Shader→текстовый дамп — выбрать простое).
4. Документация: раздел «Writing an extractor plugin» в CONTRIBUTING
   или docs/plugins.md: интерфейс, гарантии, пример.

## Критерии приёмки

- [ ] Пример-плагин из `examples/` ставится рядом и его экстрактор
      появляется в `--list-extractors` и вызывается при unpack
- [ ] Сломанный плагин (импорт бросает исключение) — warning,
      распаковка продолжается встроенными
- [ ] Плагин с `obj_type = "Texture2D"` переопределяет встроенный
      с предупреждением в логе
- [ ] Документация с рабочим примером копипастом
- [ ] Тесты: фейковый плагин регистрируется через entry points
      тестового пакета (или monkeypatch importlib.metadata)

## Тесты

- `tests/unit/test_plugin_loading.py`: загрузка из мока
  `importlib.metadata`, конфликты, изоляция ошибок, приоритет.
- Интеграционный тест с примером-плагином: skip если examples-пакет
  не установлен (в CI — шаг установки примера перед тестами).

## Риски и открытые вопросы

- Безопасность: плагины — произвольный код; это нормальная
  python-модель расширений (как у pytest), зафиксировать в доке
  «ставьте только доверенные пакеты».
