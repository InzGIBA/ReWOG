# T-17: Пошаговый режим сборки

- **Статус:** не начата
- **Приоритет:** high
- **Оценка:** M
- **Зависимости:** T-01 (состояния разборки), T-02 (glTF-анимации)
- **Квартал roadmap:** Q4 2027

> Базовые задачи должны быть в статусе «готово» до старта этой.

## Цель

Промежуточное между «взрыв-схемой» и «анимацией»: последовательность
шагов сборки/разборки, как в игре. Два выхода: папка сцен-шагов
(каждый шаг — GLB, статичный, для презентаций/статей) и один GLB со
ступенчатой анимацией (плавная сборка по шагам) — наследует инфраструктуру
анимаций T-02.

```bash
wog-dump build-scene ak47 --assembly-steps          # папка шагов
wog-dump build-scene ak47 --assembly-steps --animated  # + GLB с анимацией сборки
```

## Контекст: что будет доступно после базовых задач

- T-01: `core/scene_states.py` с `apply_exploded()` и данными фазы R
  о порядке разборки (списки `_parts`/`_field_strip` — если порядок
  в данных есть, он там; если нет — эвристика T-01 зафиксирована).
- T-02: `core/anim.py::AnimationTrack` и `GLBWriter.add_animation()`
  — готовый способ записать движение частей как glTF-анимацию.
- `SceneStats.parts` / `SceneStats.field_strip` — списки частей.

## Требования

### Функциональные

- `--assembly-steps N`: N сцен-шагов в
  `runtime/scenes/<weapon>-steps/step_01.glb ... step_N.glb`.
  Шаг i = оружие, собранное на i×(1/N) частей (порядок добавления —
  обратный порядку разборки из данных T-01; рядом со сборкой —
  «стол разборки» с ещё не установленными частями, как в state
  `field-strip` из T-01).
- `--animated` (требует `--assembly-steps` или работает отдельно
  с дефолтным числом шагов): один GLB `assembly.glb`, где анимация
  (треки T-02) переводит оружие из exploded-состояния в собранное
  по шагам — каждая часть едет из своей exploded-позиции в
  целевую линейно; сглаживание на стыках шагов не обязательно.
- `steps.json`-манифест: число шагов, части на каждом шаге, ссылки
  на файлы, длительность анимации.
- `--steps-from field_strip`: строить шаги только из списка
  field-strip (неполная разборка — типовой учебный сценарий),
  дефолт — полный `_parts`-список.

### Нефункциональные

- Код пошаговой логики — в `core/scene_states.py` рядом с функциями
  T-01 (переиспользует те же `PartPlacement`); генерация треков —
  `core/anim.py`. Новых модулей не плодить.
- Все шаги строятся за один проход по бандлу (одна загрузка
  UnityPy-окружения), не N загрузок.

## План реализации

1. Функция `build_steps(tree, part_order, n) -> list[SceneTree]`
   (чистая, поверх типов T-01).
2. Цикл эмиссии шагов в `build_scene()`; манифест.
3. `--animated`: генерация AnimationTrack-ов из позиций
   exploded→assembled (по одному треку на часть), запись через
   `add_animation()` из T-02.
4. CLI-флаги, справка, README.

## Критерии приёмки

- [ ] `--assembly-steps 5` для ak47: 5 GLB, открыты в Blender,
      каждый следующий шаг содержит больше собранных частей
- [ ] `--animated`: GLB, проигрываемый в Blender/three.js как
      непрерывная сборка; проверен gltf-валидатором
- [ ] `steps.json` корректен и согласован с файлами
- [ ] Чистые функции покрыты тестами (порядок частей, разбиение
      на шаги, генерация треков: времена монотонны, значения из
      exploded в assembled)

## Тесты

- `tests/unit/test_scene_states.py` (расширение): build_steps на
  синтетическом дереве, граничные случаи (частей меньше шагов,
  пустой список).
- `tests/unit/test_anim.py` (расширение): треки генерации шагов.

## Риски и открытые вопросы

- Если порядок разборки в данных игры не выражен (итог фазы R из
  T-01), использовать эвристику «от мелких внешних к крупным
  внутренним» (по глубине узла в иерархии + габаритам) —
  зафиксировать выбор в докстринге и манифесте (`"ordering":
  "heuristic"`), чтобы не выдавать за игровой порядок.
